# 数据合规与安全边界

> 本文说明数据流、密钥管理、PII、保留与删除、以及「演示版 vs 生产版」的差距。目标是让接入方清楚知道哪些已经做了、哪些必须自己补。

## 1. 数据分类

| 类别 | 示例 | 存放 |
| --- | --- | --- |
| 密钥 | `CHAT_API_KEY` / `EMBED_API_KEY` / `RERANK_API_KEY` / `LANGFUSE_*` | 仅 `.env`（gitignore） |
| 用户输入 | 问句、订单号、手机号（用户自述） | MySQL `messages` / `low_confidence_questions` / `review_queue` |
| 业务数据 | 订单/物流/售后（演示为 mock） | 不落库，工具内存生成 |
| 知识 | FAQ/政策/手册/规格 | `data/kb/*.md` + MySQL `knowledge_chunks` + Milvus |
| 审计 | 工具名/参数/结果摘要/状态/耗时 | MySQL `tool_audit_logs` |
| 观测 | trace、prompt、检索结果、token、耗时 | Langfuse（自部署） |
| 评估 | 评估集、报告、编造台账 | `tests/data` + `data/*/reports` + MySQL |

## 2. 密钥管理（已实现）

- 所有密钥只从 `.env` 读取，`.gitignore` 覆盖 `.env`、`.env.*`，仅放行 `.env.example`；
- 代码、测试、文档、dev-notes 中不出现真实密钥；
- 测试注入占位值，不打真实上游；
- Langfuse key 为自部署本地占位。

> 生产建议：改用 Vault/KMS/云 Secret，禁止把 `.env` 挂进镜像或流水线日志。

## 3. 第三方数据流（需知悉）

| 去向 | 内容 | 说明 |
| --- | --- | --- |
| 聊天上游 | 用户问题、对话上下文、证据、工具结果 | 用于生成回答/意图/自评/摘要 |
| 嵌入上游 | 知识块文本、检索 query | BGE-M3 |
| 重排上游 | query + 候选证据 | bge-reranker |
| Langfuse | trace（可选） | 自部署，默认内网 |

> 接入方需确认上游厂商的数据使用条款；涉敏场景应使用私有化模型或脱敏后再调用。

## 4. PII 与脱敏

- 演示版**不做**登录/实名，用户输入可能包含订单号、手机号；
- `messages`、`low_confidence_questions`、`review_queue` 可能留存原话；
- ch10 语料清洗有「脱敏/纠错/格式」步骤，但主链路写入未做统一脱敏；
- 工具结果只挑回答需要的字段（已实现字段裁剪），降低泄露面。

> 生产建议：入库前统一 PII 识别与掩码（手机号/地址/证件），审计与观测端同样脱敏；提供用户删除权。

## 5. 访问控制与审计

- 演示版**无鉴权**，仅以 `user_id` 归属会话；不建议直接暴露公网；
- 工具调用全量审计（`tool_audit_logs`）：会话、tool_call_id、工具名、来源、参数、结果摘要、状态、错误、重试、耗时；
- 被权限拒绝/校验拦下也落审计；
- 审计写失败不影响业务（不反拦）。

## 6. 保留与删除

- 当前**未实现**自动保留期与删除任务；
- 建议：会话/消息按 N 天归档或删除；问题池与待审按处理状态清理；评估报告按轮次滚动；
- 删除时需同时处理 MySQL、Milvus（按 chunk id）、Langfuse（trace）与本地报告。

## 7. 模型输出合规

- 负面知识：不承诺到账/到货/维修时效、不承诺赔偿金额、不臆造订单物流；
- 证据不足显式拒答，不硬编；
- 回答带引用编号，可回溯章节与原文；
- 投诉走安抚 + 转人工/建工单，不自动承诺。

## 8. 许可证与依赖

- 本仓库 MIT；
- 第三方依赖各自许可证（LangChain/LangGraph/FastAPI/Milvus/pymilvus/Langfuse/RoBERTa 等），商用前请逐项核对；
- 知识库内容为演示数据，上线前替换为企业真实政策并走法务审核。

## 9. 已知合规缺口（必须由接入方补齐）

1. 鉴权/租户/RBAC；
2. PII 脱敏与删除权；
3. 数据保留期与自动清理；
4. 上游数据处理协议（DPA）；
5. 审计日志的完整性保护（防篡改）；
6. 等保/隐私政策/用户告知。
